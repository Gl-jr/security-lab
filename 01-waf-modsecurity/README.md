# Лабораторная 01. WAF: защита веб-приложения от SQL-инъекций и XSS

## Цель

Развернуть уязвимое веб-приложение за Web Application Firewall, провести атаки
с WAF и без него, разобрать журнал WAF и сравнить режимы блокировки и обнаружения.

## Схема стенда

```
Браузер ──► :8080 ──────────────────────► DVWA ──► MariaDB     (без защиты)
Браузер ──► :8081 ──► WAF (ModSecurity) ──► DVWA ──► MariaDB     (через WAF)
                         │
                         └──► logs/audit.log (JSON)
```

| Компонент | Образ | Назначение |
|---|---|---|
| DVWA | `ghcr.io/digininja/dvwa` | Намеренно уязвимое веб-приложение |
| MariaDB | `mariadb:10` | База данных DVWA |
| WAF | `owasp/modsecurity-crs:nginx` | nginx + ModSecurity v3 + OWASP Core Rule Set, режим reverse proxy |

Порты опубликованы только на `127.0.0.1`: уязвимое приложение недоступно из сети.

## Запуск

```bash
docker compose up -d
```

## Ход работы

### 1. Атака без защиты

DVWA → SQL Injection (Security Level: Low), ввод `1' OR '1'='1`.
Результат: выведены все 5 пользователей из таблицы — инъекция успешна.
Запрос к БД превращается в `WHERE user_id = '1' OR '1'='1'`, условие истинно для каждой строки.

### 2. Та же атака через WAF

Результат: `HTTP 403 Forbidden`, запрос не дошёл до приложения.

### 3. Анализ журнала

```
python3 waflog.py
```

```
[17:25:17] 172.18.0.1  HTTP 403  /vulnerabilities/sqli/?id=1'+OR+'1'='1
   правило 942100 | 2 | SQL Injection Attack Detected via libinjection
   правило 949110 | 0 | Inbound Anomaly Score Exceeded (Total Score: 5)

[17:16:06] 172.18.0.1  HTTP 403  /login.php?q=<script>alert(1)</script>
   правило 941100 | 2 | XSS Attack Detected via libinjection
   правило 941110 | 2 | XSS Filter - Category 1: Script Tag Vector
   правило 941160 | 2 | NoScript XSS InjectionChecker: HTML Injection
   правило 941390 | 2 | Javascript method detected
   правило 949110 | 0 | Inbound Anomaly Score Exceeded (Total Score: 20)
```

OWASP CRS работает по модели **anomaly scoring**: каждое сработавшее правило добавляет баллы
(CRITICAL = 5, ERROR = 4, WARNING = 3, NOTICE = 2), а правило 949110 блокирует запрос,
если сумма достигла порога `ANOMALY_INBOUND` (здесь 5).

| Семейство правил | Атака |
|---|---|
| 930xxx | LFI — подключение локальных файлов |
| 932xxx | RCE — выполнение команд |
| 941xxx | XSS |
| 942xxx | SQL-инъекции |
| 949xxx | Итоговое решение по входящему запросу |

### 4. Режим DetectionOnly

`MODSEC_RULE_ENGINE: "DetectionOnly"` → та же атака проходит (`HTTP 200`, выведены все пользователи),
но в журнале фиксируются те же правила 942100 и 949110. WAF принимает решение, но не применяет его.

## Выводы

1. **Зачем внедрять WAF сначала в DetectionOnly.** Чтобы собрать картину легитимного трафика
   и выявить ложные срабатывания до включения блокировки. Ложная блокировка реальных клиентов —
   прямой ущерб для бизнеса.
2. **Ложное срабатывание (false positive)** — блокировка легитимного запроса. Устраняется анализом
   действий пользователя и точечным исключением: не отключение правила целиком, а исключение
   конкретного правила для конкретного параметра на конкретном URL. Альтернатива — повышение порога
   anomaly score.
3. **Ограничения WAF.** Не видит атаки вне HTTP (SSH, RDP, SMB), атаки на бизнес-логику
   (IDOR: подмена `id=5` на `id=6`), вход по украденным учётным данным, обращения к серверу
   в обход WAF по прямому IP, уязвимости нулевого дня без сигнатур. WAF — один из слоёв
   эшелонированной защиты, а не замена безопасной разработке.
