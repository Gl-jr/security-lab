# Лабораторная 03. Wazuh: SIEM и обнаружение атак на хостах

## Цель

Развернуть Wazuh (открытая SIEM/XDR-платформа), подключить агента, сгенерировать атаки,
разобрать сработавшие правила и **написать собственное правило обнаружения**.

## Стенд

```
        MacBook M1 Pro (хост, 16 ГБ)
        ┌──────────────────────────┐   ┌──────────────────────────┐
        │  ВМ seclab (Ubuntu ARM)  │   │  ВМ endpoint (Ubuntu ARM)│
        │  Wazuh manager  :1514/15 │◄──│  Wazuh agent  (endpoint-1)│
        │  Wazuh indexer           │   │  auditd (Linux audit)     │
        │  Wazuh dashboard :443    │   │  цель для имитации атак    │
        └──────────────────────────┘   └──────────────────────────┘
              192.168.104.1                   192.168.104.3
```

| Компонент | Роль |
|---|---|
| **Wazuh manager** | приём событий, применение правил, создание оповещений |
| **Wazuh indexer** | хранение и поиск (OpenSearch) |
| **Wazuh dashboard** | веб-интерфейс: `https://localhost:8443` |
| **Wazuh agent** | ставится на защищаемый узел, собирает журналы и события аудита |

Wazuh развёрнут в виртуальных машинах (Lima + Virtualization.framework), т.к. официальные
контейнеры собраны только под x86, а хост — Apple Silicon (ARM). Пакеты Wazuh под arm64 существуют.

**Важно:** агент и менеджер нельзя ставить на одну машину (пакеты конфликтуют) — агент всегда
разворачивается на отдельном узле, за которым нужно следить. Поэтому создан второй узел `endpoint`.

## Ход работы

### 1. Развёртывание и подключение агента

Агент подключается к менеджеру по портам 1515 (регистрация ключа) и 1514 (передача событий).
Команда установки генерируется мастером в интерфейсе (Deploy new agent → DEB aarch64 →
адрес сервера → имя агента). После запуска агент виден в списке со статусом **Active**.

### 2. Атака №1: перебор паролей SSH

С endpoint выполнено 32 попытки входа несуществующими пользователями.
Результат в Wazuh:

| Правило | Уровень | Описание |
|---|---|---|
| 5710 | 5 | sshd: Attempt to login using a non-existent user (23 события) |
| **5712** | **10** | sshd: brute force trying to get access to the system |

**Ключевой вывод — корреляция.** Правило 5710 фиксирует одиночную попытку (шум). Композитное
правило 5712 срабатывает, когда 5710 повторилось `frequency: 8` раз за окно времени, и делает
вывод «идёт перебор». Одиночное событие — шум, серия — инцидент. Привязка: MITRE T1110 (Brute Force).

### 3. Атака №2 и собственное правило: чтение /etc/shadow

Цель — обнаружить кражу хэшей паролей, для которой нет встроенного правила.

**Шаг 1 — сбор данных (на endpoint).** Правило Linux-аудита помечает чтение файла:

```
# /etc/audit/rules.d/shadow.rules
-w /etc/shadow -p r -k shadow_read
```

Агенту указано читать журнал аудита (в `ossec.conf`):

```xml
<localfile>
  <log_format>audit</log_format>
  <location>/var/log/audit/audit.log</location>
</localfile>
```

**Шаг 2 — правило обнаружения (на сервере, `/var/ossec/etc/rules/local_rules.xml`):**

```xml
<group name="local,audit,">
  <rule id="100100" level="12">
    <if_group>audit</if_group>
    <field name="audit.key">shadow_read</field>
    <description>Чтение файла паролей /etc/shadow: возможна кража хэшей</description>
    <mitre>
      <id>T1003.008</id>
    </mitre>
    <group>authentication_failures,pci_dss_10.2.1,</group>
  </rule>
</group>
```

Разбор полей:
- `id="100100"` — диапазон 100000+ зарезервирован под собственные правила;
- `level="12"` — выше, чем у brute force (10): кража хэшей опаснее перебора;
- `if_group>audit` — реагировать только на события подсистемы аудита;
- `field name="audit.key">shadow_read` — условие: метка, поставленная правилом аудита на endpoint;
- `mitre>T1003.008` — техника «OS Credential Dumping: /etc/passwd and /etc/shadow».

**Шаг 3 — проверка.** Чтение `/etc/shadow` на endpoint → метка `shadow_read` в аудите →
агент отправил событие → правило 100100 подняло тревогу уровня 12. Подтверждено в интерфейсе
(фильтр `rule.id : 100100`): описание, уровень, MITRE-техника, агент endpoint-1, `data.audit.exe`.

## Цикл создания детекта (главный итог)

1. **Определить угрозу** — кража хэшей из /etc/shadow.
2. **Настроить сбор данных** — правило Linux-аудита на конечной точке.
3. **Написать правило корреляции** — своё правило Wazuh с уровнем и привязкой к MITRE.
4. **Проверить** — сгенерировать событие и убедиться, что тревога сработала.

Встроенных правил не хватает на все угрозы, поэтому инженер по мониторингу дописывает свои
под конкретные риски компании. Это и есть основная работа с SIEM.

## Выводы

1. **SIEM ценен корреляцией, а не сбором.** Отдельные события — шум; связанные во времени —
   инцидент. Правило 5712 из 8 неудачных входов делает один вывод «атака».
2. **Полезен и обратный сигнал** — прекращение потока событий от агента означает, что узел
   отключён или атакующий отключил отправку. Следить нужно и за тишиной.
3. **MITRE ATT&CK** даёт общий язык: T1110, T1003.008 — так аналитики и продукты понимают
   друг друга при описании атак.

## Управление стендом

```bash
# запуск сервера и узла
limactl start seclab && limactl start endpoint
# интерфейс
open https://localhost:8443
# остановить, когда не нужно (освобождает ОЗУ)
limactl stop endpoint && limactl stop seclab
# полное удаление стенда
limactl delete -f endpoint && limactl delete -f seclab && rm -rf ~/SecLab
```

Ресурсы: seclab 4 ГБ, endpoint 1,5 ГБ. На 16 ГБ ОЗУ перед запуском стоит закрывать тяжёлые
программы, иначе система уходит в нехватку памяти.
